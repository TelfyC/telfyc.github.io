# 教 AI 拧螺丝：一个 IoT App 的对话模块诞生记

> 别人做 AI 对话是为了聊天，我们做 AI 对话是为了让模型隔着蓝牙去拧一台真机的 16 路 IO 模块。
> 模型的幻觉放在聊天里是段子，放在工控现场是事故。这篇博客讲讲我们怎么用 STAR 法则把这件事干成的。

---

## S — Situation：用户的手指头快不够用了

我们的 App 是一个 React Native 写的 IoT 设备管理工具，通过蓝牙 BLE + KCP 协议连接 A / V / G / H 四个等级的设备。

「等级」是什么概念？G 级设备有 57 条控制指令，A 级 30 条，V 级 18 条，加起来 105 条设备指令，背后是几十个子页面：IO 配置、总线收发、串口监测、PID 参数、VLAN、终端电阻……每个页面都有自己的表单、自己的协议帧、自己的坑。

现场工程师的典型一天是这样的：

- 想把 IO 模块第 3 通道设成 4-20mA？点进 5 个页面，确认 3 个弹窗；
- 想看 CAN2 现在跑了多少帧？先连蓝牙、等 KCP 握手、进总线监测页、选对通道；
- 想给 8 个子设备统一改个串口波特率？……建议先吃个饭。

与此同时，全行业的 App 都在接大模型。我们老板的原话大意是：「别人有的我们也要有，但我们这个得**真能控制设备**，不能只会背说明书。」

于是任务就来了。

## T — Task：三条军规

把大模型塞进一个蓝牙工控 App，目标拆开来是三条军规：

1. **不能幻觉**。模型说「已为你重启设备」的时候，设备必须真的收到过那条重启帧——不能是模型脑补的重启。
2. **危险操作必须过确认**。重启、恢复出厂、改 IP 这类操作，AI 想干可以,先弹窗给人类过目,人类点头才能下发。
3. **体验要像个 2026 年的产品**。流式输出要顺、Markdown 要能渲染、能语音输入、结果不能只甩一坨文字——要有能直接点的卡片。

翻译成工程语言：给模型一本「能力员工手册」，一个「工具执行器」，一套「UI 组件白名单」，再配一个「危险操作纪委」。

## A — Action：一路升级打怪的一百多个坑

挑几个最有戏剧性的讲。

### 第一幕：给模型发员工手册（DeviceCapabilityRegistry）

大模型最大的问题是自信——它自信地觉得全世界的设备都长一个样。对工控来说这是致命的：A 级设备的通道号是 **0-based**，G 级总线有 CAN1/CAN2 之分但 **CAN-FD 只有 CAN1 支持**，H 级有屏幕、G 级没有……

我们的解法是把全部设备能力做成一份注册表 `device-capability-registry.json`：5 个设备类目、105 条指令、每个参数的取值范围全写进描述里（——是的，registry 的结构化 `range`/`enum` 字段后端根本不消费，**描述文本是值域抵达模型的唯一路径**，所以 65 个参数的 desc 我们一条一条手写补齐的）。

这份文件从 v1.0 一路迭代到 **v1.13**，前后端围绕它交接了五次。交接纪律也是血泪换来的：曾有一次合并基线选错，差点把对方整段独有内容静默删掉，从此定下规矩——**diff 必须逐行误删审计，协议文档只按 hunk 合并，禁止整份覆盖**。

### 第二幕：模型回的不是话，是 UI（20 种卡片组件）

传统 AI App 的做法是模型输出文字，App 原样贴出来。但「串口当前波特率 9600、数据位 8」这种话，用户看完还是得自己去页面上改——那我们这个 AI 不就是个点读机吗？

所以我们建了 `UIComponentRegistry`：模型可以回结构化组件——开关组、滑块、曲线图、串口监测面板、总线发送器……前端把它渲染成**能直接交互的卡片**。

组件库从 0 长到 **20 种**（外加一个 UnsupportedCard 兜底），过程堪比一部物种进化史：

- `slider` 曾被约定成「一切模拟量调节都用它」，结果真机一用：模型给的 min/max 是错的，初值被静默 clamp、超量程被静默削顶——**用户以为设了 20mA，设备收到的是量程上限**。连夜砍出 `analogOutput` 输入框面板，把「slider 万能」收窄成「slider 只管屏幕亮度」；
- 电源模块没有 IO 通道（`channels: null`），串口 COM 口也不是 IO 通道，但组件库全是「以 channelNo 为中心」设计的——好，再补 `powerPanel` / `portConfig` / `portMonitor` 三兄弟；
- 最离谱的是超时语义：A 级串口监测的 `TIMEOUT` **必须当成功**（fire-and-forget，没回话是常态），而 G 级总线监测的 `TIMEOUT` **是真失败**（有独立 ACK，该回没回就是丢了）。同一个错误码，两种截然相反的判词——我们内部称之为「薛定谔的超时」。

### 第三幕：测试绿得发光，真机黑得发慌

危险确认是我们的纪委系统：模型调用危险指令时，后端先发 `confirm_request`，App 弹窗，人点了确认才真下发。

第一版我们给弹窗做了漂亮的结构化渲染——按指令名从 registry 查出参数定义，逐条翻译成人话。单测写得妥妥帖帖，36 个用例全绿。

然后真机一测：重启设备，弹窗显示「即将执行以下操作」——一个参数名都没渲染出来。

排查结论让人想砸键盘：后端实发的 `confirm_request` **只有 `{callId, summary}` 两个字段**，我们测试里构造的 `name`/`args` 契约字段后端根本没实现。也就是说，36 个绿得发光的用例，全都在测一个真机永远走不到的分支——结构和边界完全脱节的典型教学事故。

教训刻在了墙上：**单测造数据之前，先拿真机抓一份真实报文**。

### 第四幕：跟一台会「记仇」的模型斗智斗勇

更玄学的还在后面。真机联调时，对 AControl 设备说「重启」,模型干脆拒答：「该指令暂不支持您的设备。」

这就邪门了：工具白名单里有 restart，前端的 `restartAny` 也没有任何缺口。深挖之后真相大白——模型在做**型号匹配排除**：registry 里 A 类登记的 models 全是 CPL 耦合器系列，而 AControl 这个类靠 `inherits` 继承 A 级指令,模型侧看不到继承语义,一看型号对不上,直接拒答。

更刺激的是，同一台设备上次明明弹过确认框——**模型「肯不肯调」本身就是不稳定的**。而且一旦它在某个会话里拒过你，它会带着这个先验一直拒下去。那段时间我们排查 SOP 里都加了一句：

> 复测前请清空对话开新会话，否则你在跟一台记仇的 AI 谈判。

### 第五幕：语音输入三连环

语音输入用的是 sherpa-onnx 本地 ASR，一套 int8 模型 198MB（设计文档里写「85MB」是早期误记——就像跟妈说衣服打了五折，数字听着舒服就行）。内置进 release APK，首启自动解包。

真机首调直接踩了三个连环坑：

1. `adb push` 进外部存储，App 死活读不到——模型文件必须 `run-as` 进内部存储；
2. 传 `modelType: 'auto'` 直接 NPE——旧架构必须显式写 `modelType: 'transducer'`；
3. 音频不足一个识别窗口就调 decode，native 层 `SHERPA_ONNX_EXIT` **直接把整个进程扬了**，exit 255，连个 Java 异常都不给你留——静默程度堪比暗杀。

修完之后新增规矩一条：decode 之前先问 `isReady`。跟 native 库打交道，礼貌是刚需。

### 第六幕：那些藏在角落里的小妖怪

篇幅有限，快速点名：

- **对话列表向上滚会「闪现」**：FlashList v1 的估算高度重排是元凶，换成 FlatList + MVCP 治好了——但 Android 的 `removeClippedSubviews` 默认 true 会让 MVCP **静默失效**，必须显式关掉。Android：我帮你优化掉了你的优化；
- **流式渲染**：80ms 节流 + 流式期间纯 Text、结束后才上 Markdown 的双态方案，治好了边输出边解析 Markdown 的抽搐；
- **AI 对话挂在原生 Modal 里**，意味着 `MyBottomModal` 永远被压在下层——所以卡片里的枚举项一律行内展开，弹中弹是禁术；
- **KCP/BLE 链路**修了 ACK 校验绕过、重组重同步、写入重试、死链上报四处——蓝牙信道是物理世界，物理世界不讲武德。

## R — Result：数字说话

从第一行代码到全链路可用，大约两周、39 个提交，交卷成绩如下：

| 指标 | 数字 |
| --- | --- |
| 设备能力指令 | 105 条（G 57 / A 30 / V 18，H 与 AControl 继承） |
| 暴露给模型的工具 | 100 个（白名单制，后端校验兜底） |
| 需人工二次确认的危险指令 | 28 条 |
| AI 卡片组件 | 20 种 + 1 兜底，全部真机可交互 |
| 能力注册表迭代 | v1.0 → v1.13，前后端五轮交接 |
| 前端单测 | 56 个测试文件、622 例全绿 |
| 后端 e2e 回归 | 全部 PASS，危险指令拒答/确认行为有模型侧实证 |
| 服务层代码 | 约 5000 行（最大单文件 `DeviceControlService.js` 3204 行——它值得一篇自己的传记） |

用户侧的变化一句话就能说清：以前「把 3 号通道设成 4-20mA」要点 5 个页面 3 个弹窗，现在是打一句话、看一眼确认弹窗、点「确认」。

## 尾声

这个模块最深刻的教训不是架构，而是**双方都在假装确定性的东西最危险**：模型假装它认识你的设备，测试假装它见过真实报文,组件假装它懂量程,超时假装它是失败。

AI 工程的本质，大概就是把这些「假装确定」一个个揪出来，换成白名单、契约、结构化校验和人工确认——然后才敢按下「下发」。

下期预告（如果还有下期）：远期待办 B16/B17——让 AI 学会多步编排设备工作流。到时候模型要拧的就不是一颗螺丝，而是整条流水线了。祝我们好运。
